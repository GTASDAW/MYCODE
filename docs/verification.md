## 真实数据库结果

起步版中，100 个不同用户通过独立事务同时竞争一个活动的 10 个名额：成功 10 个，满员拒绝 90 个，最终有效报名记录和活动人数均为 10。候补版本的同一场景结果见下方“候补报名迭代验证”。测试使用虚拟线程并发任务和 20 个数据库连接，验证一致性，不把这个结果当作系统吞吐量指标。

50 个不同活动各自同时发生首次报名：50 个全部成功，没有死锁。这个用例覆盖了同活动竞争测试看不到的空报名键间隙锁问题。

另外验证了重复报名、重复取消、重新报名、已开始活动、外键插入失败后的事务回滚、权限检查、CSRF 轮换和重启初始化不覆盖已有数据。

## 候补报名迭代验证

本轮加入候补状态 `WAITING`、候补计数和自动递补；现有报名与取消接口的行为扩展为：满员报名返回 200 并进入候补，取消有效报名在同一事务中递补排队最早的一人，取消候补只退出队列。管理概览增加 `waitingRegistrations`，报名名单增加 `WAITING` 筛选。浏览器回归在同一个浏览器中依次切换管理员和普通用户会话，避免混用登录状态。

## 运行边界

当前演示地址是本机 `http://127.0.0.1:5173`，服务保留运行，尚未发布到公网。

仓库提供 Docker Compose、前后端 Dockerfile 和 Nginx 同源配置，并加入隔离容器的自动检查。当前 Windows 机器没有 Docker，本机没有执行容器构建；远程执行的真实结论以本轮记录和 Actions 为准。

JDK 与 MySQL 使用项目内的工具目录，本地服务只绑定回环地址。启动脚本会核对端口进程，停止脚本只终止记录并核实过的本项目进程。已实际验证本项目停止与重启后，其他项目的服务仍保持运行。

Session 当前在单个 Java 进程的内存中，重启后需要重新登录；数据库活动和报名记录保留。Redis、多实例部署、支付、文件上传和公开注册不在第一版中。

# 报名锁定查询优化：假设、对照与正确性

本轮检查 `ActivityMapper.lockById` 的冗余读取，并用同一 CI 主机上的旧、新应用做对照。旧版本固定为 `ccfb35f04432d9b9d54996b84be3832ac55773f9`。2026-10-08 的 [首次性能基线](performance-report.md) 说明了检查方向，但它与本轮不是同一次测量，不能把两次不同主机的数字直接算成优化收益。

本轮已完成真实 SQL 证据、38 项本机后端回归和同一 CI 主机的四段 HTTP 对照。7200 次正式报名与 1600 次独立写预热全部返回 200，一致性和精确清理均通过。同活动 50 并发的吞吐中位数提高 6.62%、批 P95 中位数降低 7.18%；这是本次固定条件下的观察，重复范围仍有重叠，不能宣称统计显著或生产环境稳定提升。

本页以下方法和数字记录的是 2026-10-09 固定 V2 实验，不代表当前 V3 源码仍只有三个锁定字段。活动取消功能新增 `cancelled_at` 后，当前 `ActivityLockRow`/`lockById` 需要四列以判断关闭状态；COUNT 和展示字段仍不参与锁定投影。历史结果、计划和 7200/1600 样本数保持原样，不用新功能数据重写旧收益。

复现这份历史对照需在独立干净 checkout 检出候选基准 `d781648d7d9036b653a80e3082b609358a59df35`，按该提交的工作流执行。当前 `scripts/compare-signup.sh` 会核对迁移目录、`ActivityMapper` 和 `RegistrationService` 是否与固定实验兼容，发现 V3 或业务变化就提前拒绝，不能在当前生命周期版本上混用旧应用得出前后提升。常规 `performance` 任务继续测当前单版本 18 批，最新业务合同见 [活动生命周期](activity-lifecycle.md)。

## 从调用路径找到冗余读取

报名请求沿 `ActivityController` → `RegistrationService.register` → `lockOpenActivity` → `ActivityMapper.lockById` 执行。取消请求也进入 `lockOpenActivity`。这两个写流程在 `READ_COMMITTED` 事务内先锁活动主键行，再普通读取报名状态。

旧锁定查询映射为公开展示用的 `ActivityRow`：

```sql
SELECT id, title, description, location, starts_at, capacity, registered_count,
       (SELECT COUNT(*)
        FROM registrations rw
        WHERE rw.activity_id = activities.id AND rw.status = 'WAITING') AS waiting_count,
       NULL AS registration_status
FROM activities
WHERE id = ?
FOR UPDATE;
```

`lockOpenActivity` 只使用 `starts_at` 判断活动是否已开始；`register` 再使用 `registered_count` 和 `capacity` 决定有效报名或候补。标题、介绍、地点、候补人数和报名展示状态没有参与这些业务判断。

报名和取消结束前均调用 `ActivityService.get`，通过原有详情查询读取更新后的完整活动数据，包括真实 `waitingCount` 和当前用户状态。旧版本在锁定查询里提前统计的候补人数，既没有用于分配名额，也没有作为最终响应返回。

COUNT 是锁定 SELECT 内部的相关子查询；它不是一次额外的 JDBC 往返。删除这个子查询减少数据库内部工作和结果映射字段，不应描述为“少请求一次数据库”。旧版本每次写操作仍只发出一次锁定 SELECT。

## 最小改动及保留的行为

内部锁定查询使用职责明确的 `ActivityLockRow`，只映射写流程实际需要的三个字段：

```sql
SELECT starts_at, capacity, registered_count
FROM activities
WHERE id = ?
FOR UPDATE;
```

没有新增表、迁移、索引、缓存或连接池配置。公开列表、详情和管理查询仍使用各自的完整展示字段，候补 COUNT 仍查询真实报名记录。取消时的 FIFO 查询及状态、人数更新次序也保持原有设计。

| 阶段 | 旧、新版本共有行为 |
| --- | --- |
| 活动获取 | 在 `READ_COMMITTED` 事务中按主键 `FOR UPDATE`，不存在返回 404；取得锁后检查开始时间 |
| 当前报名 | 在活动锁保护下普通读取该用户报名，保持 `(activity_id, user_id)` 唯一约束 |
| 报名 | 有名额成为 `ACTIVE` 并加一次人数；满员进入 `WAITING`，重复请求幂等 |
| 取消与递补 | 取消 `ACTIVE` 后在同一事务中递补最早候补；取消 `WAITING` 不改变有效人数 |
| 返回详情 | 在同一事务内再次读取真实详情和候补人数；随后事务提交、释放活动锁 |
| 失败 | 状态、人数、递补和返回查询中出现异常时，事务一起回滚 |

行锁的持有时间不等于 `lockById` 的执行时间。拿到锁之后的报名状态读取、写入和最终详情查询仍位于同一个事务内。收窄投影不会消除热门活动之间必要的串行处理，也不能把行获取 Timer 直接解释为 MySQL 纯锁等待。

## 可检验假设与执行计划

假设是：删去没有使用的候补统计和展示字段，可能减少锁定阶段的 SQL 执行与映射开销；当候补记录增加时，旧查询的统计成本可能更明显。该假设不意味着 COUNT 已被证明是主要瓶颈，也不意味着客户端 P95 必然改善。

执行计划应在同一个隔离 MySQL、同一活动和相同候补记录上分别检查两条完整 SQL。查询前核对数据身份，查询后的状态也应保留不变量。普通 `EXPLAIN` 用于说明访问路径与估计，不用估计行数充当实测耗时；如执行 `EXPLAIN ANALYZE`，必须明确它会真正执行查询及锁定，并在受控事务内结束。

`V2__add_waiting_registration_status.sql` 已有 `(activity_id, status, updated_at, id)` 候补索引。2026-10-09 已在本机真实 MySQL 8.4.11 的独立 `activity_platform_test` 中，对一场 10 个名额、10 条 ACTIVE、90 条 WAITING 的活动取得 `EXPLAIN FORMAT=JSON`，再分别实际执行一遍完整锁定 SELECT。证据保存在忽略目录 `.runtime/ci/query-plan-evidence.json`；测试记录只在同一连接事务内创建，结束回滚后核对原表计数与归属记录保留情况。

| 证据 | 本轮状态 |
| --- | --- |
| 数据规模与清理 | 10 ACTIVE / 90 WAITING；测试事务回滚后，原有表计数不变，临时归属记录为 0 |
| 旧查询计划 | 活动使用 PRIMARY、估计 1 行；COUNT 相关子查询使用 `idx_registrations_waiting` 覆盖索引、估计 90 行 |
| 新查询计划 | 活动使用 PRIMARY、估计 1 行，不再包含候补子查询；返回字段从 9 个减少为 3 个 |
| 实际 SELECT 的 Handler 增量 | 旧查询 `Handler_read_key=2`、`Handler_read_next=90`；新查询分别为 1、0，均只执行一次锁定 SELECT |
| 后端回归 | 本机 38 项测试通过，失败、错误、跳过均为 0；保留真实 MySQL 的并发、重复操作、候补 FIFO、回滚及真实详情检查 |

计划中的 90 是优化器估计值；这里另有实际 Handler 增量支持旧子查询确实额外遍历了候补索引。Handler 是存储引擎读取操作计数，不等于物理磁盘 I/O、纯锁等待或客户端耗时。该微型对照证明减少了不需要的数据库工作，单凭这一证据不能证明热门活动吞吐或 P95 改善。没有使用 `EXPLAIN ANALYZE` 或重置全局统计来得到这些结果。

## 同一主机上的版本对照

对照使用同一隔离 Compose 项目 `gather-perf-ci`、数据库 `activity_platform_perf`、MySQL 与 Nginx，以及相同前端和请求脚本。旧、新后端镜像都在这次 CI 中从各自完整提交构建，不复用上一次运行的测量结果。

Java 和 MySQL 容器各固定 2 CPU、1024 MiB，连接池、默认内存 Session、Cookie/CSRF、数据库参数保持一致。负载生成器仍与服务共享 CI 主机；因此本实验比较的是这组受控条件下的两个版本，不能推导公网延迟或生产容量。

运行顺序是 **A1 → B1 → B2 → A2**，A 为旧查询，B 为收窄后的查询。每个区块重新启动目标版本的后端 JVM，重启 Nginx 刷新上游 DNS，重新登录并执行一致的写路径预热，然后运行相同的 18 个批次。MySQL 容器和数据卷保持不变；镜像源码标签和实际 JAR 指纹用于核对每段的真实版本。交错次序可以暴露前后时段的漂移，不能消除共享主机调度、JIT、数据库缓存和 GC 的全部影响。

每个区块的测量配置：

- 两个场景：100 个用户争 10 个名额的同活动场景，以及 100 个用户各报名一场活动的不同活动场景。
- 并发 1、10、50；每个场景和并发组合重复 3 次。
- 每批 100 次真实 HTTP 报名，共 18 批、1800 次；四个区块合计 **72 批、7200 次计时请求**。
- 每段先有 20 次活动列表读取，再用同活动/不同活动两场景、并发 1/50、每组合 100 次执行 400 次写预热；四段另有 1600 次预热报名，单独验证并精确清理，不混入 7200 个正式测量样本。读预热、准备、登录、数据库断言和清理也不计入报名耗时。
- 每批结束验证准确状态和人数，再精确清理本批活动/报名、恢复固定数据基线；不能让 A/B 处理不同数量的历史报名。

脚本的 Docker 项目、回环端口、数据库身份和唯一探针验证继续保留；版本切换不扩大可写环境或清理范围。每个区块完成时检查归属数据清理及原始行保留，再启动下一个版本。

当前测量合同是 `gather-signup-v2-write-warmup`。每段完整成功运行应精确清理 **1112 场活动、2200 条报名、100 个合成用户**：909 场正式活动 + 202 场写预热活动 + 1 场绑定探针。预热和正式批次都恢复同一准备基线，最后清理用户与探针；实际结果以各段 JSON 为准。2026-10-08 v1 的 910/1800 清理数字只属于历史读预热方法。

## 指标怎么比较

客户端耗时从报名请求发出到完整读取并解析 JSON，保留每个请求的原始样本。吞吐量用该批完成数除以批次墙钟时间；客户端 P95 使用 100 个实际样本的 nearest-rank，服务端近似窗口 P95 不替代它。

| 指标 | 比较口径及限制 |
| --- | --- |
| 吞吐量 | 每批完成请求数 / 批次秒数，报告重复批次的波动 |
| 客户端 P95 | 每批 100 个原始耗时计算；汇总各批 P95 的范围时明确它不是合并样本后的全局 P95 |
| 活动行获取均值 | 前后累计 Timer 总耗时、计数作差，只代表这一批的 SQL 执行与锁等待合计 |
| 连接池 | 固定间隔采样的 active/pending 最大值；当前 `poolSamples` 明确包含批前、周期和批后，短批次仍可能没有周期采样，0 不证明没有占用 |
| HTTP 与业务状态 | 分别记录 200、4xx、5xx、网络失败，以及 `ACTIVE` / `WAITING` 的准确数量 |

每个版本每个场景/并发组合有两区块各三批，共六次重复。汇总时保留区块和批次，不只挑最快一次。若计算变化百分比，必须指明它是哪些批次的哪一种统计量，不能把各组 P95 的均值称为整体 P95。

测量方法与过去的读预热基线不同，新的写路径预热会改变状态。只在本轮 A/B 使用相同预热、脚本和资源时作版本对比，不将旧报告的某个低点或高点当作本轮 A。

同活动和不同活动的并发 10/50 组，在两对阶段中都观察到吞吐上升、批 P95 下降；但是六组的旧、新批 P95 范围全部有重叠。并发 1 的吞吐方向不一致：同活动第一对 −1.18%、第二对 +6.03%；不同活动第一对 −2.22%、第二对 +8.70%，不同活动的批 P95 中位数总体还上升 4.49%。不能把总体中位数向好写成每个批次都提升。

本轮结论是保留这个最小改动：它已证明减少业务不使用的 SQL 工作并让内部类型职责更清晰，当前固定条件下的并发组也出现有限改善；尚未证明 COUNT 是整个系统的主要瓶颈，未进行统计显著性推断，也不宣称生产环境稳定提升或更大的持续容量。活动行锁、事务、FIFO 与真实详情查询保持原设计。

同一数据库和精确清理控制了可见行数据，却不重置 AUTO_INCREMENT、InnoDB 后台 purge、数据库/操作系统缓存；这些状态在四段间继续演进。每段新 JVM 与一致的写预热也不保证 JIT、GC 达到完全相同稳态；共享主机调度与采样开销仍可能影响结果。每批只有 100 请求，50 并发约两波，没有代表长时间稳态负载。

四段 JSON 保留全部 7200 个正式耗时、1600 个写预热样本、错误/状态、数据库与清理证据；汇总另保留阶段范围、配对变化和每版本/组的 600 原始样本合并分位数。完整产物见本次 [对照任务](https://github.com/GTASDAW/MYCODE/actions/runs/37869706975) 的 `signup-query-comparison` 附件，保留 7 天；本页保存经核对的长期结论，不把已过期附件描述为永久可下载。

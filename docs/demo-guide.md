# 五分钟演示：从报名到候补递补

这份流程用于本机演示和面试讲解。先启动本项目，打开 `http://127.0.0.1:5173`；使用容器环境时打开 `http://127.0.0.1:8088`。演示账号为 `admin / Admin123!` 和 `demo / Demo123!`。流程不依赖公网服务，递补与活动取消写入本项目站内通知，不发送邮件或短信。

## 演示前准备

- 确认活动列表能打开，`/api/health` 返回 `UP`。
- 使用一场新活动，不修改已有样例活动的报名。标题带唯一时间，例如“面试演示 20261009 1530”，开始时间设为北京时间明天 20:00，名额设为 **1**。
- 每次切换身份先通过账号菜单退出，再登录另一个账号。管理员也可以参加活动，因此仅用两个预置账号就能演示候补递补。
- 预先打开 [架构与接口说明](architecture.md)、[并发报名复盘](concurrency-review.md) 和 [验证记录](verification.md)。实际测试结果以验证记录和当前 CI 运行为准。

## 可选的两分钟账户流程

演示自主注册时，先从登录页进入“注册账号”，填写一个未使用的用户名、昵称和密码。注册成功会回到登录页，账号已填入，需要自己登录；服务端只创建普通用户，不能从表单选择管理员。

用新账号报名一场未来活动，再从账号菜单打开“个人中心”，修改昵称并保存。账号菜单随即显示新昵称，刷新个人中心后仍保留；退出再登录，“我的报名”仍有刚才的记录。登录名保持固定，昵称只作为展示资料。

解释 `uq_users_username`、密码哈希和可信登录 ID：重复用户名由数据库唯一约束决定；昵称修改不接受其他人的身份；资料读取查数据库最新值，不替换整个 Session 身份与 CSRF。若准备两个独立窗口，可展示重新打开个人中心后读取新昵称，以及退出一个会话不会使另一个退出。当前没有跨窗口推送，不能说成所有已打开页面自动同步。代码路径见 [账户指南](account-guide.md#按一次请求阅读代码)。

## 可选的一分钟活动发现演示

匿名打开“发现活动”，按自己发布的唯一标题或地点查询，切换“报名中”“已满员”“已取消”，确认上方统计表示整个筛选范围。匹配活动超过 12 场时可以翻页，每页数量也可改变；少量结果正常只有一页，不需要修改已有样例数据制造页数。

从筛选结果打开详情，刷新后点“返回活动列表”，条件仍保留。也可以从详情登录并报名，再返回列表，检查个人状态和剩余名额更新；搜索条件写入 URL，分享的是条件而不是固定数据快照。失败可重新加载，空结果可清除筛选。代码与一致性解释见 [活动发现指南](activity-discovery.md)。

## 五分钟流程

| 时间 | 操作 | 讲解重点 |
| --- | --- | --- |
| 0:00–0:45 | 管理员登录，打开概览，然后发布上述 1 个名额的新活动 | 统计来自真实 MySQL；React 提交表单，后端校验管理员身份并保存活动 |
| 0:45–1:30 | 退出后在发现页搜索唯一标题，从详情登录 `demo` 并报名，再返回筛选结果或查看“我的报名” | 登录后回原详情，返回列表保留查询条件；报名成为 `ACTIVE`，人数从 0 变为 1，统计重新读取 |
| 1:30–2:30 | 换 `admin` 登录，进入同一活动，点击“加入候补”；取消候补，再重新加入 | 满员后成为 `WAITING`，有效人数仍为 1；取消候补不会影响已报名用户，重新加入按新的入队时间排队 |
| 2:30–3:15 | 换 `demo` 登录，取消有效报名；再换 `admin` 打开通知中心，从递补消息进入详情 | 系统在同一事务内把最早候补者递补为 `ACTIVE` 并生成一条通知，有效人数仍为 1，候补人数变为 0 |
| 3:15–4:00 | 管理员打开活动管理，搜索唯一标题，进入报名名单，切换“已报名”“已取消”筛选；再打开概览 | 管理表格与公开详情共用真实数据；名单中 `admin` 已报名、`demo` 已取消；每个管理接口由服务端校验权限 |
| 4:00–5:00 | 打开运行指标、事务代码和当前验证结果 | 解释活动行锁、幂等、FIFO、回滚与测试；说明单实例统计、客户端性能测量与两种 Session 模式 |

结束时管理员可以取消自己在演示活动的报名，使该活动有效人数回到 0。手工发布的演示活动会保留，系统当前没有活动删除接口。自动测试创建的临时数据使用单独的精确清理机制，不应以标题前缀批量删除。

## 可选的活动编辑与取消演示

用另一场尚未开始、名额为 1 的新活动单独演示整场取消：

1. 管理员从详情进入“编辑活动”，修改标题、介绍和地点，保存后刷新详情；开始时间和名额只读且不变。
2. 用 `demo` 报名，再用 `admin` 加入候补，确认有效人数 1、候补人数 1。
3. 管理员点击“取消活动”，填写原因并确认；详情显示“活动已取消”、原因和北京时间，有效人数与候补均为 0。
4. 在报名名单查看两条保留的已取消记录；活动管理选择“已取消”，概览的取消活动数增加。换 `demo` 打开“我的报名”，也能看到同一原因。
5. 说明重复的有效取消请求保留首次原因和时间、活动不可恢复；已取消详情不能继续报名。手工演示不需要直接改数据库或触发自动测试清理。

讲解报名与组织者取消的两种锁顺序：报名先成功也会随后被整场取消；取消先提交时，后续报名返回 `ACTIVITY_CANCELLED`。两者最终人数均为 0，而历史 ID 保留。真实 MySQL 对锁顺序、开始边界与异常回滚的证据见 [活动生命周期指南](activity-lifecycle.md#实际验证与阅读路径) 和 [验证记录](verification.md)。

## 可选的一分钟通知演示

在上述真实递补之后，`admin` 点击顶栏铃铛或“通知中心”，找到这场唯一标题的“候补递补成功”消息，点击“标记已读”；当前页重新读取，铃铛显示本人全部未读数。切换未读/已读筛选、刷新 URL 或翻页，条件保留；重复标读保留第一次时间，打开详情本身不会自动标读。

使用另一场形成有效报名和候补的新活动做整场取消，两个当时参与者分别登录后打开通知中心，查看相同公开原因；此前已经自行取消的人不收到这类消息。没有轮询，其他窗口产生变化后需打开或刷新通知页。强调标题和原因是事件快照，当前详情是最新活动信息；普通用户不能查看或标读他人的通知。完整条件和代码路径见 [站内通知指南](notification-guide.md)。

## 代码怎么讲

按一个请求的实际路径讲清楚，不必逐行背代码：

1. `frontend/src/api.ts` 统一发送 HTTP 请求和 CSRF 信息，认证状态由现有 AuthProvider 管理。
2. `SecurityConfiguration` 根据 Cookie Session 识别用户；服务端校验权限与 CSRF，报名人来自可信登录身份。
3. Controller 接收活动 ID，`RegistrationService.register` / `cancel` 开启 `READ_COMMITTED` 事务。
4. `ActivityMapper.lockById` 使用 `SELECT ... WHERE id = ? FOR UPDATE` 锁定这场活动；随后普通读取报名状态。
5. 满员报名进入 `WAITING`；取消 `ACTIVE` 后，`RegistrationMapper.findEarliestWaiting` 按 `updated_at ASC, id ASC LIMIT 1` 取最早候补者，更新状态和人数并插入递补通知后一起提交。
6. 接口返回真实最新状态，页面更新；刷新直达仍从数据库读取记录。

现有 [架构图](architecture.md#技术分工) 展示 React、统一入口、Spring Security、Controller、Service、MyBatis、MySQL 和两种 Session 存储方式。双实例的会话流向另见 [共享 Session 指南](shared-session.md)。

## 面试追问与回答依据

| 问题 | 当前实现的回答依据 |
| --- | --- |
| 为什么锁活动，而不是只检查人数？ | “读取名额→改状态→改人数”必须串行；所有该活动的写操作先拿同一行锁，避免多人同时读到剩余名额 |
| 为什么报名记录普通读取？ | 状态变更已受活动行锁保护；`READ_COMMITTED` 能读到前一个事务提交后的状态，避免查询不存在的报名键时增加无用间隙锁 |
| 连续点击报名或取消会怎样？ | 活动开放时，已 `ACTIVE` / `WAITING` 的报名返回当前结果；重复用户取消不改变人数。整场取消保留首次原因和时间，关闭后报名与用户取消返回 409 |
| 组织者取消会删除用户历史吗？ | 不删除；有效与候补改为 `CANCELLED`，人数归零，已取消记录原 ID/更新时间保持，用户可查看活动原因和时间 |
| 通知写入失败会不会报名成功但消息丢失？ | 两类站内通知都加入已有业务事务；插入失败会回滚状态和人数，插入后业务失败也会回滚消息。当前没有外部投递，不能把数据库事务保证直接用于邮件 |
| 为什么同一用户可能收到两条递补通知？ | 取消后再次候补并真正递补是新事件，需要新通知；重复同一次取消请求不会再次转换状态，也不会多生成消息 |
| 标记已读或翻页会改变未读数口径吗？ | 首次标读只更新本人消息一次并保留时间；未读数始终统计全部本人通知，与当前页、未读/已读筛选无关 |
| 写入到一半报错会怎样？ | 状态变化、人数变化和递补处于同一个事务，异常回滚；现有真实 MySQL 用例直接验证了先更新人数、再插入报名失败时，人数与报名记录一起回滚 |
| 100 人竞争 10 个名额证明了什么？ | 原并发用例验证最终 10 条 `ACTIVE`、90 条 `WAITING`，有效人数等于活动人数；它只证明该场景一致性。性能报告另记录固定资源下的客户端延迟和吞吐量，不能宣称任意流量都可接受 |
| Redis 解决什么问题？ | 可选方案让两个 Java 实例共享登录身份和 CSRF；名额与候补一致性仍由 MySQL 保证。默认内存模式不需要 Redis，重启后重新登录 |
| 同时注册同一个名字怎么办？ | 服务端先规范化为小写，`uq_users_username` 是最终保障；一个请求插入成功，另一个返回 409。密码用既有 BCrypt12 保存哈希，注册不会自动获得管理员权限或登录 |
| 多个会话的昵称怎么保持最新？ | `/auth/me` 按可信 ID 读取数据库；Session 身份快照不整体改写。其他会话下一次读取才看到更新，退出只使当前 Session 失效 |
| 为什么分页卡片只有 12 张，统计可能超过 12 场？ | SQL 的聚合覆盖整个筛选集合，与当前页在同一次 UTC 时间和只读快照中读取；前端不从一页卡片推算总数与剩余名额 |
| 从详情回来为什么要再请求？ | 用户可能刚报名或取消，URL 保存的是查询条件；重新读取才能取得最新个人状态、总数和统计，结果减少时还要修正越界页码 |
| 运行指标里的 P95 是系统 P95 吗？ | 是当前实例某一路由/状态在近 5 分钟窗口的近似值；不能平均各接口或各实例的 P95。固定负载报告另用 100 个客户端原始样本计算 |
| 活动记录获取耗时为什么不能叫锁等待？ | 计时包括 SQL 执行、通信与行锁等待，不能独立识别 MySQL 纯锁等待；应结合场景对比和连接池采样进一步检查 |
| 怎么证明收窄锁定查询有收益？ | 先确认锁定结果中的候补 COUNT 和展示字段未被使用，再在同一 CI 主机交错运行旧、新版本，保留写预热、72 批原始样本和一致性断言；依据实际重复结果作有限结论，不用不同机器的历史数字直接算提升 |

演示结束可以邀请面试官挑一个小变化，例如调整名单筛选或说明某次重复请求的状态。重点是自己能够定位请求、解释业务不变量和验证方式。

运行指标演示可先访问一场活动，再以管理员进入 `/admin/monitoring` 手动刷新，核对实例编号、累计请求和路径模板；多实例刷新可能切换实例，不能把两个计数直接相减。浏览器网络面板中的 `X-Request-Id` 可关联该次 JSON 日志。性能数字只引用 [实际评测报告](performance-report.md)，同时说清资源、并发、样本数、错误和正确性断言，不宣称任意规模的高并发能力。

需要讲优化案例时，打开 [查询优化复盘](query-optimization-review.md)，按“代码发现 → 假设 → 最小改动 → 同条件对照 → 实际结论”展开。强调活动主键行锁、FIFO 和返回时的真实候补查询仍保留；COUNT 原本是锁定 SQL 中的子查询，不能把移除它说成消除一次数据库往返。

## 可选的一分钟共享登录演示

使用 Redis Compose overlay 时，先登录，在浏览器网络面板观察 `/api/auth/me` 的 `X-Gather-Backend` 响应头：重复读取会分配给不同后端，但身份一致。然后仅在自己启动的这组本地演示中重启 A：

```powershell
docker compose -f compose.yaml -f compose.redis.yaml restart backend
```

等待 `/api/health` 恢复后刷新页面，会话未过期且 Redis 可用时，仍保持同一登录。最后退出，再说明两个后端都无法恢复原身份。完整的跨实例 CSRF、权限、退出和闲置失效证据以验证脚本及 [验证记录](verification.md) 为准；3 秒 TTL 演练只在隔离 CI 执行，不修改手工演示环境。

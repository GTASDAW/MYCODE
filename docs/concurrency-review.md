# 如何避免并发报名超额

这个项目的核心问题是：一个活动只有 10 个名额，如果 100 个不同用户同时报名，系统最多只能确认 10 人，其余用户按顺序进入候补；活动人数必须和 `ACTIVE` 报名记录数一致，取消后只能递补一位候补用户。

本文说明设计和验证方法。测试是否实际通过，以运行测试时的输出为准。

## 为什么先查再写会出错

假设活动名额是 10，已经有 9 人报名。两个请求分别查询剩余名额，都看到还有 1 个名额。如果它们接着各自写入报名记录，就会接受两个人。

```text
请求 A：读取人数 9，判断可以报名
请求 B：读取人数 9，判断可以报名
请求 A：创建报名记录
请求 B：创建报名记录
```

如果人数更新使用 `人数 = 人数 + 1`，最终会得到 11，超过名额。如果两边都把自己读到的 9 加一后写回 10，人数显示是 10，却有 11 条有效报名记录。仅仅让单次 SQL 更新是原子的，还不足以让整段业务正确。

## 三种机制各解决什么

| 机制 | 保证 | 单独使用的不足 |
| --- | --- | --- |
| `(activity_id, user_id)` 唯一约束 | 同一用户和活动最多一条报名记录 | 100 个不同用户仍然可以分别进入有效报名或候补 |
| 数据库事务 | 报名状态与人数一起提交或一起回滚 | 未串行化容量判断时，多个事务仍可能同时看见空位 |
| 活动记录的行锁 | 对同一活动的容量判断与状态变更按顺序执行 | 仍需要事务和正确的业务规则来保护多条写入 |

项目组合使用这三种机制。报名、取消和候补递补采用 `READ_COMMITTED` 事务，先锁活动记录，再用普通 `SELECT` 读取报名记录并修改状态。所有会改变报名人数或候补状态的入口必须遵循同一套锁顺序。

活动锁已经串行化同一活动的全部报名状态变更，因此不需要再锁报名查询。特别是首次报名时记录尚不存在，如果在默认 `REPEATABLE READ` 下对空键使用 `FOR UPDATE`，可能锁住共同的索引间隙，让不同活动的首次插入互相等待。`READ_COMMITTED` 配合普通报名查询避开这类搜索间隙锁；唯一约束仍负责防止重复记录。这一取舍依据 [MySQL 8.4 的行锁、间隙锁与插入意向锁规则](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)。

## 报名与取消算法

以下是业务伪代码；实际 SQL 和返回类型见后端实现。

```text
报名：
  开启 READ_COMMITTED 事务
  锁定活动记录（SELECT ... FOR UPDATE）
  活动不存在 -> 拒绝
  活动已开始 -> 拒绝
  普通 SELECT 读取当前用户的报名记录
  已 ACTIVE 或 WAITING -> 返回当前报名结果，不修改人数
  有空位：没有记录 -> 创建 ACTIVE；记录已取消 -> 恢复为 ACTIVE；活动人数加一
  已满员：没有记录 -> 创建 WAITING；记录已取消 -> 改为 WAITING 并刷新排队时间
  提交事务

取消：
  开启 READ_COMMITTED 事务
  锁定活动记录（SELECT ... FOR UPDATE）
  活动不存在 -> 拒绝
  活动已开始 -> 拒绝
  普通 SELECT 读取当前用户的报名记录
  没有记录或已经取消 -> 返回已取消结果，不修改人数
  WAITING -> 改为已取消，不修改人数
  ACTIVE -> 改为已取消，活动人数减一
  ACTIVE 释放名额后，按 updated_at ASC、id ASC 取最早 WAITING，改为 ACTIVE，活动人数加一
  提交事务
```

两个用户争最后一个名额时，第一个请求持有活动行锁并完成报名，第二个请求等待。第一个提交后，第二个取得锁并读取最新人数，发现已经满员，因此创建候补记录并返回 `WAITING`，不会增加有效报名人数。

同一个用户重复点击时，请求也要依次取得活动行锁。后到的请求看到已经有效报名或已在候补，就返回现有结果，不重复加人数或重复排队。取消后重新报名使用原记录；满员时恢复为候补并刷新排队时间，唯一约束仍然成立。

幂等行为限于活动仍开放时：重复操作不会重复改变人数，取消有效报名只递补一位候补。活动开始后的请求统一拒绝，不能借由重复调用继续修改报名或候补队列。

## 怎样验证，而不是只看代码

并发测试使用真实 MySQL，验证 InnoDB 的行锁和事务行为。用内存数据库替代 MySQL，不能充分证明这套设计在目标数据库上成立。

### 100 个用户争 10 个名额

1. 创建一个尚未开始、名额为 10 的活动，准备 100 个不同用户。
2. 给每个请求使用独立的数据库事务。如果经 HTTP 调用，每个用户也需要独立的登录会话和有效 CSRF 令牌。
3. 用共同的起跑信号放行并发任务；连接池容量可以限制同时活跃的数据库连接，但任务总数仍为 100。
4. 收集每个请求的成功、业务拒绝和意外异常，等待全部任务完成。
5. 查询数据库，断言 `ACTIVE` 报名数为 10、活动人数为 10，两者相等；其余请求应创建 `WAITING` 候补记录，不得增加活动人数。

这个测试证明的是给定环境和负载下的一致性，不代表系统能承受任意流量。运行记录应同时注明 MySQL 版本、连接池和工作线程设置、结果及耗时。

### 还要覆盖的场景

- 同一用户并发报名多次：只有一条报名记录，人数只增加一次。
- 满员后报名进入候补：返回 200 和 `WAITING`，候补计数增加，重复请求保持幂等。
- 有效报名取消后只递补排队最早的一人；候补记录按 `updated_at ASC, id ASC` 排序，其他候补保持 `WAITING`。
- 候补用户取消只退出队列，不占名额，也不触发其他候补递补。
- 不同活动同时首次报名：为尚无报名记录的两个活动同时发起请求，全部应成功，各自人数与记录数一致，不能因空键间隙锁发生跨活动死锁。
- 同一用户连续或并发取消：人数只减少一次，不能变为负数。
- 取消后重新报名：有空位时恢复同一条记录并增加一次人数；满员时恢复同一条记录为候补，不增加人数。
- 报名与取消同时发生：结果符合取得活动锁后的执行顺序，人数与有效记录数始终相等。
- 活动开始后报名或取消：拒绝请求，数据库状态不变。
- 在已经发生一次写入后制造异常：事务回滚，人数和报名状态都恢复，不能留下半完成的数据。
- 普通用户直接调用管理员创建接口：后端拒绝，不能只靠前端隐藏入口。

回滚测试要让异常出现在事务中间，并在事务结束后用新的查询确认数据库状态。仅验证异常抛出，不能证明数据库已经正确回滚。

## 面试时如何解释取舍

可以先说明不变量：人数不超过名额，并且等于 `ACTIVE` 报名记录数；`WAITING` 记录按排队顺序递补。接着用“两个用户争最后一个名额”和“取消后递补”解释竞态，再分别说明唯一约束、事务和行锁的作用。最后给出真实测试结果以及失败事务的验证方式。

活动行锁使同一活动的报名串行执行，逻辑直接，适合当前规模。热门活动的吞吐量受到持锁时间和数据库连接数影响，因此事务内只做必要数据库操作，不调用外部服务。将来如果要优化，应先测量等待时间，再评估限流或条件更新等方案，同时保持同样的不变量。

Session 当前存放在单个 Java 实例内存中，这是部署边界，与数据库行锁解决的问题不同。多实例登录共享和热门活动流量控制需要各自设计，加入 Redis 也不能自动替代数据库事务与约束。
